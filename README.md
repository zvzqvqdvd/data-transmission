# 数据传输

一个绿色免安装的单文件工具。双击运行后，在同一个局域网内让任意多台设备互传文字、文件和桌面；不在同一网络时，还能通过 WebRTC 点对点直传。

> **下载**：Windows 程序就在本仓库根目录 —— **[数据传输.exe](数据传输.exe)**（约 9.4 MB，绿色免安装，双击即用）。本仓库同时是**完整项目源码**：`数据传输.py`（后端）+ `web/`（界面六文件）+ `index.html`（导出产物），clone 下来就能改、能打包、能发布，详见「仓库结构（GitHub）」。在线页 `https://zvzqvqdvd.github.io/data-transmission/` 的入口页底部也有「下载 Windows 程序」按钮；本机没装程序就点「创建房间」时，页面会直接把下载按钮和「已启动，重新创建」摆出来。

## 能做什么

- **多人房间**：房主开一个房间，外网和局域网都能进，**没有人数上限**（局域网几十台、外网同时连多台都行），所有人看到同一份聊天记录
- **文字聊天**：微信风格界面，消息带时间与来源（谁发的都标出来），落盘保存，2 秒内自动同步，不用刷新
- **文件互传**：多选上传、逐字节无损、下载、删除；同名文件自动加序号，不会覆盖；文件只存在房主设备上，其他设备在聊天里点文件卡片按需下载，不会自动往每台设备塞一份
- **发送队列**：每个文件一张卡片，逐项显示 等待 / 传输中（百分比 + 实时速度 + 剩余时间）/ 完成 / 失败，可以单个移除重发
- **拖拽与粘贴**：把文件拖进窗口直接进队列；截图后 Ctrl+V 粘贴直接发送
- **网络与中继设置**：右上角 🌐 可以添加自定义 STUN/TURN（TURN 带账号密码），配置只存在本机浏览器；
  成员清单里会标出每台设备走的是「直连」还是「中继」，连不上时按原因给出对应建议
- **使用帮助**：右上角 ？ 内置常见问题（房间码失效、桌面共享要求、手机限制等），不用翻 README
- **临时房间，数据不永久保存**：房间在三种情况下自动销毁——关闭房主页面（刷新不算，回来就继续）、
  连续 12 小时没有任何通信、房主点「销毁房间」。销毁时本机的聊天记录与接收文件一并删除
- **按需下载**：聊天里的文件只显示一张卡片，点卡片本身就开始下载，不会自动往每台设备塞一份；访客下载时卡片下方直接显示进度条。卡片上不放下载图标（同一字符在手机 / 电脑 / iOS 上渲染不一致），点卡片本体就是下载
- **桌面共享**：一键把自己的屏幕实时推给房间里所有人看，WebRTC 直连；30fps / 1080p 采集、6 Mbps 码率上限、优先保帧率，清晰度和流畅度都比老版本高一档；可带上系统声音（对方能调音量、静音）；画面就显示在聊天流里，不占满整屏。**仅限外网设备（走媒体流），局域网设备不参与共享观看**
- **免责声明**：入口页底部一行「☑ 我已阅读并同意《免责声明》并同意继续使用」，复选框**默认勾选**（不弹窗）；点「《免责声明》」**整页打开独立声明页**（dp-title「免责声明」+「返回」按钮 + 全文滚动区），声明共七条（用途限制/合法使用/内容责任/数据与隐私/服务无担保/责任限制/条款变更与生效，含发布日期）。未勾选时点创建/加入 → toast 提示先勾选，不放行。复选框为微信风圆形绿底白勾样式
- **新加入的人能看到前面的记录**：房间历史会推给刚进来的设备，刷新、晚到都不会一片空白
- **统一入口**：打开同一个网址，选「创建房间」或「加入房间」，两种身份进的是同一套界面
- **局域网直连**：同一 WiFi 下用内网地址访问，输入房间码即可加入，不绕外网，本机页面顶部就有可复制的地址与二维码
- **房间码只在这一次运行里活着**：点「创建房间」才生成，销毁/退出程序后作废，下次点「新建房间」会生成新的
- **设备管理（仅房主端）**：房主能看到两条通道各连了几台设备、各自的匿名编号与 IP；其他设备（外网访客、局域网设备）一律不显示人数与 IP，后端也不会把设备清单下发给它们（只看不管，没有踢人功能）
- **完全离线**：`data-transmission/index.html` 可以直接发给任何设备，用浏览器打开就能用

## 怎么用

### 第一步：启动程序

**程序从哪来**：打开在线页 `https://zvzqvqdvd.github.io/data-transmission/`，点入口页底部的「下载 Windows 程序」，或者直接下 `数据传输.exe`（就在这个仓库根目录）。**创建房间失败时入口页也会直接把下载按钮摆出来**——本机没装程序、或者装了没启动，都按提示走。

双击 `数据传输.exe`。Windows 弹出 UAC 时点「是」，这是为了让程序自动放行 8000 端口。启动后会弹出一个**控制台窗口**，服务自动开始运行，窗口里只显示几行启动状态：申请管理员权限放行防火墙、启动看门狗、服务启动成功、外网访问链接。保持窗口开着就是服务运行中，**关闭窗口或按 Ctrl+C 即停止服务**。

**此时还没有房间**——要在页面里点「创建房间」才会生成房间码。

### 第二步：打开这个地址

**在这台运行程序的设备上打开** → 点「创建房间」，进入后就是房主：

- **打开页面时不会自动开房**：程序启动后只是等着，点了「创建房间」才生成房间码、建房间文件夹
- **等房间真正就绪才进主界面**：点下去按钮变成「正在创建房间…」、左边 ＋ 换成旋转圆环；
  **进度就画在这行文字正下方**——「✓ 检查本机程序 · ✓ 创建房间 · › 连接外网通道」+ 百分比 + 一条细进度条，
  不再用下方黄色横条播报「房间已创建，正在等待连接就绪…」。
  只有「后端开好房间」+「外网直连的房主 Peer 在信令服务器注册成功（PeerJS open）」两件事都完成，才切进房间。
  所以进房后不会再挂一句「正在连接信令服务器…」。以前为了让人看清动画人为拖的 1 秒已经删掉，信令快就快进；
  信令实在连不上（最多等 9 秒）也照样进房，局域网功能不受影响。刷新恢复房间走同一套等待
- **右侧信息栏**（窗口够宽时靠右竖排，窄屏才回到顶部），从上到下：**「房间」卡片**（置顶、白底，只给房主：大字房间号，点一下即复制，下面「新建房间」「销毁房间」两颗等宽胶囊）→ 局域网卡片（地址、复制/二维码、说明、「局域网已连接 N 台设备」及其设备清单）→ 外网卡片（访问链接、二维码、说明、「外网已连接 N 台设备」及其设备清单）→ **「房间说明」单独一个按钮**（点开弹窗才看完整规则）→ 房主没人时的等待提示。房间号和房间操作是房间级信息，不塞进任何一张通道卡片
- **设备数 / IP 清单、「房间」卡片和「还没有其他设备加入」等待条只给房主看**：外网访客、局域网里的其他设备都看不到，也拿不到设备清单数据
- 其他设备扫码或打开链接即可进来
- **侧栏连接卡极简**：局域网/外网卡片只有地址框 +「复制访问地址」「二维码」两枚等宽按钮 + 设备数，不再放说明文字；外网卡地址框整行展示（点击也能复制），「复制访问地址」复制的是**不带房间码**的基础链接（对方打开后输房间码加入），二维码仍带房间码、扫码免输直进；**点「二维码」是浮层模式**——二维码层直接盖在卡片上，**卡片自身尺寸与侧栏布局完全不变**（二维码固定 80px，不撑大侧栏、不挤动其他卡片），点「返回」关掉浮层
- **销毁房间**：确认后所有设备立即断开、房间码作废（旧链接和二维码都失效），**所有已打开的页面都会自动检测到房间没了并退回起始页**，
  点「创建房间」就能开一个新的。**本机的聊天记录和接收文件一并删除，不可恢复**
- **房主端连接状态行只显示连接情况**：人数已经在外网/局域网卡片里分通道显示，不再额外报一句「已进入房间 · 共 N 台设备」；其他设备的连接卡只在**还没连上**时显示连接进度，连上后一行状态文字都不留

**在任何其他设备上打开** → 点「加入房间」，输入房主给的 10 位房间码：

- 点「连接」后会**先真的连一次**：房间不存在、连不上或超时，都会一直停在入口页并给出具体原因，不会让你进一个连不上的空页面
- **其他设备统一一张连接卡（局域网 / 外网完全一致）**：只有通道名不同（「🏠 局域网」或「🌍 外网直连」），连上后都是「房间号：xxxxxxxxxx」+ 一颗浅红底的胶囊按钮「断开连接」，**不显示「✅ 已连接，可以互发文字与文件」这类状态文字，也不显示人数、IP、等待条、局域网地址或顶栏连接标签**。房间码不再挤在标题右边
- **按钮跟着连接状态走**：连接中整排按钮都不显示（还没连上按了也没用），卡片只写一行「正在连接…」及当前阶段（连接信令 / 呼叫对方 / 自动重连 / 确认房间是否还在）；**连上之后才出现「断开连接」**，同时状态行收起；彻底连不上、自动重试也停了，才给一个手动「重连」并显示失败原因。已连接期间的「接收中 / 已下载」也不写进这行，掉线重连时不会翻旧文字。局域网端点「断开连接」= 退出房间回到输码页
- 连上后界面与房主端完全一样，能发文字、传文件；桌面共享画面只有外网设备能看（局域网设备收不到媒体流）
- 邀请链接带 `?room=xxxx`，打开会自动填码，不用手输

创建房间时会先检查本机程序是否在运行。**没启动会直接报错**，不会让你进一个收不到文件的空房间。

### 同一 WiFi 下的捷径：走局域网地址

如果两台设备连的是同一个路由器，不必绕外网。**本机页面顶部有一条蓝色「🏠 局域网」**，写着类似 `192.168.1.5:8000`：

- 点「复制访问地址」把地址发过去，对方浏览器打开后**输入房间码才能进去**
- 或者让对方扫旁边的「二维码」：码里已经带着房间码，打开页面会自动填好并直接加入，不用手输
- 文字和文件走同一个路由器，速度取决于内网带宽，也不消耗流量

房间码和「加入房间」用的是同一个码，输对一次就记住（存 cookie），刷新页面不用再输；房主「新建房间」或「销毁房间」之后，这个凭证自动失效，需要重新输。

对方页面顶部会显示「🏠 局域网」，并标出所在的房间码。这类设备**不会**成为 P2P 房主，所以不会和本机抢房间码，也看不到「新建 / 销毁房间」这些房主操作。

两个前提：

- 对方要能访问你的内网 IP：同一网段即可；部分路由器的「访客网络」或「AP 隔离」会挡住
- `http://192.168.x.x` 不是安全上下文，**桌面共享只能在本机或 https 页面上发起**

### 房主和访客的区别

| | 创建房间 | 加入房间（外网） | 局域网直连 |
| --- | --- | --- | --- |
| 前提 | 本机程序已启动 | 无，任何设备都行 | 本机程序已启动 + 同一 WiFi |
| 要输房间码 | — | 要 | 要（输对一次后记住） |
| 文件存到哪 | 本机 `数据/房间/<房间码>/接收文件/` | 点卡片本体下载到浏览器下载目录，下载中卡片下方显示进度条 | 本机 `数据/房间/<房间码>/接收文件/` |
| 刷新后聊天记录 | 还在 | 重新拉一次（自动连回原房间） | 还在 |
| 能发起桌面共享 | 能 | 能，但移动端浏览器不能 | 不能（非安全上下文） |

### 房间刚建好就能发

房主建好房间后**不等别人加入也能直接发**文字和文件：消息先存进这个房间的记录（`聊天记录.json` / `接收文件/`），顶部那条橙色提示只说明「还没有其他设备加入」，不会把输入框变灰。

有人进来时，房主会把房间历史自动推给他（最多 200 条），所以刚进来的设备往上翻就能看到房主之前一个人发的内容，**不用刷新页面**。历史里的文件条目在访客端点右侧「⬇」按钮即可从房主设备把文件传过来保存。

访客（在线页「加入房间」）没有本机后端，只能真的连上房主之后才发得出去——连接过程中输入框仍是灰的。

### 一个房间能进多少设备

**没有上限**，两类人可以同时进同一个房间：

| 进来的方式 | 同时能进几台 | 消息怎么走 |
|---|---|---|
| 外网（扫邀请链接 / 输房间码） | 多台，房主逐台建立独立直连 | 房主是中继：任何人发的消息，房主落盘后转给其他所有外网设备 |
| 同一 WiFi（打开 `192.168.x.x:8000`） | 多台，只受这台电脑性能限制 | 直接读写房主本机的同一个消息文件，天然共享 |

房主端顶部会实时显示「房间里现在有 N 台设备（外网 X 台 + 局域网 Y 台）」，聊天里每个人的发言都带名字（访客默认是「手机AB / 电脑ZZ」这种，同名会自动加序号），自己发的不会重复显示。

文件走「按需下载」：任何人发的文件都只存在房主设备上，聊天里其他设备看到的是一张文件卡片，**点一下卡片就开始下载**（外网设备走点对点从房主拉取，局域网设备直接走本机 HTTP），不会自动往每台设备传一份。**所有文件一视同仁，图片不单独分类**——不自动拉取、不做缩略图预览，点卡片就是下载原文件；卡片上**不放下载图标**（同一字符在手机 / 电脑 / iOS 上渲染不一致），下载动作统一是点卡片本身。

### 外网连接速度

外网连接慢，慢的多半不是「连对方」，而是「先连上 PeerJS 信令服务器」那一步（DNS + WebSocket + 服务器回话，通常 0.3～4 秒）。

- **所有入口都预热**：页面一打开就在后台把到信令服务器的长连接建好，你输房间码的这几秒正好用来握手；点「加入房间」时只剩「呼叫对方设备」一步。实测同一网络下从 ~4 秒降到 ~1 秒，网络慢时差别最明显。邀请链接、恢复上次房间、手动输码这三条入口现在都会预热（以前只有停在入口页时预热）；预热连接放超过 90 秒或握手卡住 4.5 秒会自动换一条新的
- **连接还活着就复用**：能接着用的信令连接不重新握手；但一旦判定失败就主动换一条新的，不再反复复用「看着还 open、其实收不到东西」的半死 socket
- **别干等**：呼叫后 10 秒没通就判超时（原来 16 秒），最多两次 400ms 的短重试；同一条信令连接只挂一次 `open` 监听，重试不会累积出好几条重复呼叫
- **候选地址收发**：建立连接时同时向 4 个 STUN 服务器收地址（不加候选池——实测它会让新版 Chrome 的 DTLS 握手随机卡死），尽量少等一轮
- 预热失败不影响正常流程：真连的时候会现建一条，失败原因照旧写在入口页

### 断开连接

- **房主清场**：房间里的人只能自己离开。房主想一次性清空，用「新建房间」（换码 + 删旧数据 + 断开所有设备）或「销毁房间」
- **访客断开**：任何时候都能点「断开连接」，通知房主后关闭连接、回到入口页；连接中点它就是取消连接，会顺手停掉探活/重连/超时定时器，不会有迟到的回调又把状态改回去
- **局域网设备断开**：同一个「断开连接」按钮，点一下退出房间、回到输入房间码的起始页，可重新输码加入

断开时双方都会立刻收到，不会出现「一方以为还连着、另一方已经关了」的情况。

> 早期版本有过「把某一台设备踢出房间」的功能，现在**整体删掉了**：相关按钮、黑名单文件和接口都不存在了。
> 房间成员在房主端只以匿名编号 + IP 显示，其他设备连这份清单都看不到。

### 刷新不会掉线，但房间没了一定回起始页

- **房主端刷新**：重新抢回 `pc-<房间码>` 这个 Peer ID。如果旧连接还没被信令服务器释放，会先重试同一个码（最多 3 次），**不会一刷新就换码**把邀请链接作废。在线页带 `?host=1` 刷新时先问本机程序房间还在不在：还在就用原房间码直接回主界面（不重新开房换码），已经结束就停在起始页提示重新创建，**不会偷偷开一个新房间**
- **访客端刷新**：先探活再进主界面。房间还在就自动连回、不用重新输码；房间已经销毁就留在起始页说明原因，不会停在「正在连接」的空白主界面
- **意外断线**（对方刷新、网络抖一下）：信令还活着就**立刻**重开数据通道（通常几百毫秒），信令也断了才按 0.6s / 1.5s / 3s 退避，共 4 次，期间状态栏会写「正在自动重连…」；网络恢复（`online`）或手机解锁切回前台时会插队立刻再试一次，不用等退避定时器走完。重连期间按钮收起，连上后「断开连接」会重新出现
- **房间关闭后自动退回起始页**（不用手动刷新）：
  - 本机 / 局域网 / 在线页房主：每 2 秒问一次房间状态，房间被销毁、房间码变更就立刻回入口页；本机程序被关掉、连续 3 次（约 6 秒）问不到也会回入口页，不会卡在旧聊天界面
  - 外网访客：房主销毁时会收到通知（补发一次、延迟断开，弱网下更不容易丢）；通知没收到也没关系——信令连续两次确认找不到房主、或多次重连都失败，都会自动回起始页
  - 回到起始页时会清掉 `?host=1` / `?room=` 和本地保存的房间码，避免刷新又连回已作废的房间

## 桌面共享

点输入框右边的显示器图标，选择要共享的窗口或整个屏幕，对方页面上会自动出现画面。

- **画面在聊天里**：共享画面作为一条卡片出现在聊天流最上方，16:9 比例、桌面最大约 340 像素宽；手机屏会隐藏头像、把画面拉到整行宽（约 42vh 高）
- **手机能正常观看**：iOS Safari / 微信内置浏览器只肯播放「已经可见」且带 `playsinline` 的 video，所以代码里先把共享面板显示出来、补齐 `playsinline / webkit-playsinline / x5-playsinline / autoplay / muted`，再挂流播放。万一自动播放仍被系统拦下，画面上会出现「▶ 点击播放共享画面」，点一下用手势重新播放，不会再一片黑屏且没有任何提示
- **全屏看**：控制条上的 ⛶ 可全屏查看（iOS Safari 走 `webkitEnterFullscreen`），手机上小字画面也能放大看
- **需要 HTTPS 或本机地址**：浏览器规定只有安全上下文才能共享屏幕，所以统一入口（https）和 `127.0.0.1` 可以，`http://192.168.x.x` 不行
- **画质与流畅度**：采集按 30fps、1080p 理想值请求；每条共享链路（含房主转发的）建好后会把视频发送端码率上限放开到 6 Mbps，并设置 `degradationPreference: 'maintain-framerate'` 优先保帧率——浏览器默认只给约 2.5 Mbps，桌面文字容易糊、动起来还掉帧
- **访客之间的共享互相可见**：访客发起共享时画面原本只到房主为止；现在房主收到后会立刻把这路流转发给房间里其余外网设备，所有外网成员都能看到。房主停掉转发 / 收到「停止共享」通知时会把转发一并收掉
- **移动端只能看不能发起**：手机浏览器没有实现屏幕采集，这是浏览器限制
- **停止**：点画面右下角「停止共享」，对方画面会自动收起；共享过程中关闭共享源（比如关掉被共享的窗口）也会自动停止

## 文件下载

聊天里的文件一律只显示一张文件卡片（扩展名图标 + 文件名 + 大小）——**图片就是文件，不单独分类**，不做任何在线预览：

- **所有设备**：点卡片本体就下载（卡片上不放下载图标）
- **房主 / 局域网设备**：走本机 HTTP 直接落盘（速度最快）
- **外网访客**：从房主点对点拉取；下载中进度条直接显示在卡片下方（百分比、速度、剩余时间）
- **发送列表**：文件发送完成后，已完成的条目自动从发送列表清掉，不用再手动点「清空已完成」；发送失败的会保留，可点 ↻ 重试

不在聊天里预览是刻意的：预览得先把整个文件拉过来，流量和等待都白花，而且图片缩略图在微信 X5 / iOS Safari / 各家安卓 WebView 上的渲染差异极大——要用的时候再下载最直接，也最不容易出岔子。

## 改了源码之后

界面代码在 `web/` 目录（`page.html` 结构、`app.css` 样式、`app.js` 公共核心 / `room.js` 房间逻辑 / `gate.js` 首页逻辑、`vendor.js` 第三方库），后端在 `数据传输.py`。改哪个都不用动另一个。
三个 JS 只是**源码层面的拆分**（方案 A）：`build_page()` 按 `app.js → room.js → gate.js` 拼进同一个 `<script>`、共用一个作用域，导出后仍是**单文件 `index.html`**，访客端零外部请求、预热好的 P2P 连接不会因为跳转而丢。

只想快速看效果、不想等打包：`python 数据传输.py`，改完存盘、重开程序即可。

要让 exe 生效必须重新打包（注意 `--add-data` 把 `web/` 一起塞进去，用的是绝对路径，因为 `--specpath` 会改变相对路径的基准）：

```
python -m PyInstaller --onefile --clean --noconfirm --add-data "D:/RUANJIAN/wangzhan/局域网互传/web;web" --distpath . --workpath "%TEMP%\lanshare_build" --specpath "%TEMP%\lanshare_build" --name 数据传输 数据传输.py
```

打包前最好先关掉正在运行的旧程序，否则 exe 被占用会写不进去；不方便关时把 exe 输出到别的目录，再把旧 exe 原地改名、把新的拷进来也能换掉（正在跑的那个实例仍是旧版，关掉重开才是新版）。打包大约 20～60 秒。

**漏了 `--add-data` 会怎样**：exe 打出来只有几 MB 且启动即报错，提示"缺少页面源文件"，不会带着半截界面跑起来。

程序运行时只依赖 `client_url.txt` 和 `数据/`：前者读取在线地址，后者读写文件与聊天记录。缺了会自动创建。**房间码只存在内存里**，关掉程序房间就结束；磁盘上残留的房间记录和文件由看门狗在程序退出时清掉，不再留到下次启动。

`数据/` 下只有「房间」一个文件夹，其余全部往下一级分：**每个房间独占一个文件夹**（文件夹名就是房间码），里面就是 `聊天记录.json` 和 `接收文件/` 两样，删掉一个文件夹就等于删掉那个房间。

**每个房间的数据是分开的，但不永久保存**：房间销毁（手动、关页面、12 小时无通信）时整个文件夹当场删除；
 「新建房间」也会删掉旧房间的文件夹；程序关闭时由看门狗把这次运行遗留的房间文件夹清掉（启动时不再清理，被强杀也能收干净）。
 想留什么，请在销毁前自己把 `数据/房间/<码>/接收文件/` 里的东西拷走。

从旧版本升级时程序会自动搬迁（幂等，重名文件不覆盖）：上一版的 `数据/房间/<码>/聊天记录/messages.json` 会提上来改名成 `数据/房间/<码>/聊天记录.json`，空的 `聊天记录/` 文件夹随之删掉（里面还有别的文件就留着）；更早的 `数据/聊天记录/<码>.json` + `数据/接收文件/<码>/`、`数据/房间/<码>/messages.json`、`数据/接收文件/<散文件>`、`数据/聊天记录/messages.json` 也会一并并进对应房间（按旧版留下的房间码归位）；旧版落盘的 `房间码.txt`（`数据/`、`数据/聊天记录/`、`数据/房间/` 三处）在搬迁后删除，**不会再把上一次的房间带进新的一次运行**；搬空的旧目录自动删掉。目标位置只有 0 字节空壳时会用真实记录覆盖过去，不会因为「文件已存在」把旧记录留在原地。

`web/` 是**编译期依赖**：跑源码时要和 `数据传输.py` 同级，打包时会被塞进 exe、运行时不再需要这个目录。

## 仓库结构（GitHub）

线上仓库 `zvzqvqdvd/data-transmission` 是**完整项目**：main 分支根目录既是 GitHub Pages 的站点根目录，也放着全部源码。clone 下来就是一份能改、能打包、能直接发布的完整工程，不需要额外的私存副本。

| 路径 | 作用 | 什么时候要换 |
| --- | --- | --- |
| `index.html` | 在线页本体（`data-transmission/index.html` 的副本，单文件、零外链） | 每次改完 `web/` 重新导出后覆盖 |
| `数据传输.exe` | Windows 程序（约 9.4 MB），入口页的「下载 Windows 程序」按钮指向它 | 每次重新打包后覆盖 |
| `数据传输.py` | 后端源码（服务端、上传、鉴权、房间码、页面导出） | 改了就要覆盖 |
| `web/` | 界面源码六个文件（`page.html` / `app.css` / `app.js` / `room.js` / `gate.js` / `vendor.js`） | 改了就要覆盖 |
| `client_url.txt` | 在线地址，程序据此生成邀请链接与二维码 | 换域名时改这一行 |
| `README.md` | 本文档 | 随改动更新 |
| `.gitignore` | 排除打包中间产物与运行时数据 | 基本不动 |
| `.nojekyll` | 让 Pages 原样发布静态文件（远端已有，不用每次传） | 一次性 |

**为什么不把 `build/` `dist/` `数据/` 放进去**：前两个是 PyInstaller 的中间产物（一条命令即可重建，占了 20 MB 还每天变），后者是运行时的房间记录和你传过的文件——属于本机数据，不该进公开仓库。三样都已经写进 `.gitignore`。

页面为什么同时存在于 `web/` 和根目录 `index.html`：`web/` 是**源码**，根目录 `index.html` 是 `build_page()` 把六个文件合并出来的**产物**。Pages 只能发布静态文件，所以产物必须躺在站点根目录；源码留在这里是为了可维护、可复现——改 `web/` 里的文件，重新导出，再把产物拖上去覆盖，这条链路是唯一正确的改法。

**clone 之后怎么跑源码**

```bash
git clone https://github.com/zvzqvqdvd/data-transmission.git
cd data-transmission
python 数据传输.py
```

`web/` 是编译期依赖，必须和 `数据传输.py` 同级（仓库里就是这个位置）。缺 `数据传输.exe` 不影响跑源码，缺 `web/` 会在启动时报「缺少页面源文件」。重新打包见上面的命令。

下载地址不写死：页面按自己的基地址拼 `数据传输.exe`——从 `zvzqvqdvd.github.io/data-transmission/` 打开就下同目录那份，走自定义域名打开就下 `zvzqvqdvd.top/数据传输.exe`，**换域名不用改页面**。放根目录而不是挂 Release，是因为这样只有一个按钮、一条链接、永远指向最新版，不用维护版本号和附件；exe 离 100 MB 单文件上限还远，站点总大小也远没到 1 GB。

## 在线页部署与更新

- 主地址：`https://zvzqvqdvd.github.io/data-transmission/`
- 自定义域名：`https://zvzqvqdvd.top/`（同一份文件、同一目录，两个入口看到的页面完全一样）
- 托管：GitHub Pages（仓库 `zvzqvqdvd/data-transmission`，main 分支根目录）
- 程序的白名单里两个入口都常驻放行（`client_url.txt` 只填主地址）
- **邀请链接用哪个域名由 `client_url.txt` 决定**，文件按修改时间缓存，**改完刷新页面就生效**，不用重启程序、也不用重新导出静态页
  - 本机页面（8000）每次请求都按文件当前内容渲染，刷新即变
  - 线上那份 `index.html` 是静态文件，自己不会变，靠运行时同步：点「创建房间」时从 `/api/host` 取一次，进房后每 2 秒的 `/messages` 轮询也会带回来，**改完 `client_url.txt` 两秒内链接和二维码自动换掉**
  - 同步到的地址会存进 `localStorage`，下次刷新（哪怕本机程序还没开）也还是新地址
- 跨域白名单里的「当前在线地址」同样是实时算的，换域名后新地址直接能访问本机接口（`zvzqvqdvd.top` 与 `zvzqvqdvd.github.io` 另外常驻放行）

界面代码在 `web/` 的六个文件里，`data-transmission/index.html` 永远是它们的合并导出版本。**不要直接编辑这个文件**，改 `web/` 下的源文件、再重新导出即可。

导出的机制：程序读取六个文件，把 CSS、第三方库（`vendor.js`）和**按顺序拼接的三段业务 JS**（`app.js → room.js → gate.js`，同一个 `<script>`）内联进 `page.html` 的对应位置，拼成一份完整 HTML。所以线上仍然是单文件、零外链，`file://` 直接打开也能用。

**导出**（任选一种，效果相同）

- 命令行执行 `python 数据传输.py --export-page`
- 或者直接启动一次程序——**每次启动都会自动导出**，内容没变则跳过写入

**发布目录会自动重建**：`data-transmission/` 被误删、或者整个程序被挪到一个干净目录里，只要启动一次，目录和 `index.html` 都会重新生成出来，不用手动新建。导出发生在「单实例」判断之前，所以哪怕双击后提示「程序已经在运行了」，页面也已经补好了。控制台只显示启动状态，不再打印导出提示；需要确认是否更新，看文件修改时间即可。

2. 按这次改了什么，拖对应文件进去（覆盖同名）→ Commit changes

| --- | --- |

当前新版为 **351,067 字节**（md5 `67247a77`，页面指纹 `5ad34fab18`；对应 exe 9,436,974 字节）；线上比这个小，就是还没覆盖上传或被缓存了。**「🕒 房间说明」弹窗底部会显示页面版本**，各设备排查问题时先核对这一行是否一致。
**刷新不用重输房间码**：成功加入过的房间记在本标签页的 `sessionStorage`（`lanshare_session_room`）里，刷新页面会自动填码并静默重连，和扫码进房一样无感。它随标签页走——关掉页面重开、换浏览器仍要手动输码；正常退出房间（断开连接、被请出、房间销毁、房间码作废）时记录即清，刷新不会再自动连回旧房间。

邀请二维码 / 邀请链接带 `?v=<页面指纹>`（由 web/ 源文件算出，页面更新指纹即变）：手机浏览器对旧地址的缓存再顽固，也会因为 URL 变了而拉到最新页面——程序更新后务必让访客用**新**二维码进房。**「复制访问地址」复制的是干净地址（不带房间码、不带参数）**，电脑/桌面浏览器打开足够新鲜；手机上优先扫码进房。

**文件传输的硬约束（改代码前务必看）：**

- `CHUNK_SIZE` 必须 **小于 PeerJS 的 `chunkedMTU`（16300）**，现在取 15000。一旦超过，PeerJS 会把每片再拆成两条消息、并在接收端用 Blob 异步重组——最后一片可能比 `FILE_END` 晚一步交上来，`FILE_END` 一看字节数不齐就整包丢弃，表现就是「小文件偶尔能过、手机端传什么都不完整」。
- 所以接收端 `FILE_END` 遇到字节数不足时**不立刻丢弃**，给 2.5 秒宽限等异步重组补齐（`waitRecvComplete`）；真缺片才 `dropRecv` 清队列。
- 分片有时以 **Blob** 形式到达（微信 X5 / 部分安卓 WebView），必须走 `chunkChain` 异步读成 ArrayBuffer 再拼，不能对 Blob 调 `toArrayBuffer` 后当 null 丢掉。
- 房主发文件**必须按连接串行**（`queueConnSend`）：对端一条连接只有一个接收缓冲，两路 `sendFileTo` 并行会让分片互相穿插，两边都不完整。
- 下载看门狗按**有没有字节在动**判超时（连续 60s 无新数据才算卡住），不是按「发起多久」。以前按发起时间算 20 秒，弱网下大文件还没传完就被判超时，紧接着又发下一个请求，直接把缓冲搅乱。

## 已知限制

- 外网连接默认只用了几个公共 STUN（探测地址用），**没有内置 TURN 中继**；双方都在对称 NAT 下时可能打不通。
  需要兜底就在右上角 🌐「网络与中继」里加一台自己的 TURN（可用 coturn 自建或买云服务），配置只存在本机浏览器
- 微信、QQ 内置浏览器通常不支持 WebRTC，请用系统浏览器打开
- 访客端的消息来自房主推送：进房间时会补一份最多 200 条的历史，更早的只存在房主磁盘上；历史里的文件条目点一下卡片即可按需拉取保存
- 桌面共享多人同时看要吃掉上行带宽：房主共享时是给每台外网设备各推一路流，设备越多越吃 CPU 与上传
- 房主是外网设备之间唯一的中继：房主页面关掉，外网设备之间就收不到彼此的消息（局域网设备不受影响，它们直接连本机）
- 外网设备下载大文件走点对点直连，速度取决于双方上传/下载带宽；下载期间房主要保持页面打开
- 房主一个人也能发消息（先存进房间记录，有人加入时自动补给他）；但**访客必须真的连上房主才发得出去**，连接中断期间输入框是灰的
- 局域网直接访问 `http://<IP>:8000` 时是明文 HTTP，不适合传输敏感数据
- 管理员密码默认是 `admin`；**跑程序的那台电脑（本机访问）本身就算管理员，不用输密码**，
  局域网里的其他设备看不到管理入口（齿轮是隐藏的），设备清单只属于房主那台电脑：
  `GET /api/devices` 对它们返回 403，`/messages` 也只回人数、不回 `devices` 数组
- 房间里没有「踢人」：想一次清空所有设备就「新建房间」或「销毁房间」，房间码一换，旧链接和二维码立刻失效
- **数据不再永久保存**：房间销毁时聊天记录与接收文件一起删除，程序也不会把历史房间留在磁盘上；重要文件请及时取走

## 验证情况

多设备房间的协议与转发逻辑用 jsdom 做了回归（假 Peer + 假后端，实测通过的项）：

- 两台外网设备同时连入，房主分别分配唯一名字并回 `WELCOME` / `HISTORY` / `PEERS`
- 访客 A 发的消息：房主落盘（带 `from`、`id`），只转给访客 B，不回给 A；A 的本地消息与落盘记录同 id，不会重复
- 访客 A 传文件：房主存一份（`files` + `from` + `id` 三个字段都到达后端），再转给访客 B；A 自己不收回声

- 局域网设备发的新消息，房主轮询后转给所有外网设备；同一批消息重复轮询不会重复转发
